# Specification

- Project: `KineticChain`
- Status: 實作完成，實驗已執行
- Last updated: 2026-08-16

## Problem and Motivation

運動指導與生物力學分析的第一步，是把一段動作影片切到「關鍵時間點」上：投球的前腳著地、
高爾夫的上桿頂點、擊球瞬間、隨勢終點。這些時間點不是隨意選的畫面，而是**動力鏈**
(kinetic chain) 上力量由近端傳到遠端的節點。有了這些時間點才談得上角度量測、時序比較、
動作診斷。

現況的問題：

- 既有做法幾乎都是**一個運動一個模型**。GolfDB/SwingNet 是高爾夫專用；羽球、標槍、
  花式滑冰各自有獨立資料集與獨立模型。換一個運動就要重做整套資料、模型、訓練流程。
- 通用的 temporal action localization（如 SoccerNet action spotting）解的是「這段影片
  什麼時候發生了進球」，粒度是秒級的比賽事件，不是單一運動員動作內部的毫秒級力學節點。
- 各運動的關鍵時間點看似不同，力學上卻共用同一套結構：準備 → 蓄力 → 反向動作頂點 →
  前腳著地 → 骨盆峰值角速度 → 軀幹峰值角速度 → 上肢峰值速度 → 出手／擊球 → 隨勢。
  這個共通結構目前沒有被拿來做跨運動的知識共享。

## Goals

1. 從單機 2D 影片中，偵測指定運動項目的動力鏈關鍵時間點（輸出為影格索引）。
2. **一套流程、每個運動一個模型**：同一份程式碼、同一個模型架構、同一套訓練與評估
   指令，換運動時重新訓練（或由既有 checkpoint 微調）出該運動專屬的權重。
   不是一組權重硬吃全部運動，也不是每個運動各寫一套程式。
3. 新增一個運動項目時，只需要提供該項目的事件定義與標註資料，不需要改模型架構或重寫
   訓練流程。
4. 在高爾夫上取得與已發表基準（SwingNet, PCE 76.1%）可比較的量化結果。

> **方向修正（2026-08-16）**：初版的目標 2 寫的是「一組權重涵蓋多個運動」。
> 實驗顯示這個方向是錯的——聯合訓練在四折上一致地劣於單運動訓練（0.771 vs 0.787），
> 且使用者要的本來就是單一運動的流程。目標已改為上述版本，相關的成功標準同步調整。
> 多運動聯合訓練的程式路徑保留（`--sport` 可給多個），但不是預設用法。

## Non-goals

- 不做運動項目的自動辨識。運動項目由呼叫端指定（見 Inputs）。
- 不做動作品質評分、傷害風險評估或醫療診斷。
- 不做多人場景的追蹤與分配；輸入假設為單一運動員的已裁切片段。
- 不做 3D 姿態重建與絕對物理量（力矩、關節力）計算。

## Inputs and Outputs

### Input

| 欄位 | 型別 | 說明 |
|---|---|---|
| `video` | 路徑 | 單一運動員的已裁切動作片段。任何 OpenCV 可解碼的格式。 |
| `sport` | 字串 | 運動項目 id，必須存在於事件註冊表（`kinetic_chain/events.py`）。 |

推論也接受已抽好的姿態序列（`(T, J, 3)`，最後一維為 `x, y, confidence`），略過姿態抽取。

### Output

`EventPrediction` 清單，每個元素：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `event` | 字串 | 事件 id（如 `stride_foot_contact`） |
| `frame` | int | 影格索引 |
| `time` | float | 秒 |
| `confidence` | float | 該事件在該影格的機率 |

輸出順序保證符合該運動項目宣告的事件時序（由順序約束解碼保證，見 architecture）。

### 事件詞彙

事件 id 分兩類：

- **Canonical（跨運動共用）**：力學上定義相同、可跨運動遷移的節點。目前 10 個：
  `address`, `loading_start`, `loading_peak`, `stride_foot_contact`,
  `pelvis_peak_rotation`, `torso_peak_rotation`, `arm_peak_velocity`,
  `release_impact`, `follow_through_mid`, `finish`。
- **Sport-specific**：只在單一運動中有定義的節點（如高爾夫的 `golf_toe_up`）。

模型輸出頭涵蓋兩類的聯集，推論時以該運動的事件集合遮罩。Canonical 事件因為多個運動
共用同一個輸出槽而能互相遷移；sport-specific 事件不會。

## Scope

### In Scope

- 2D 姿態抽取（RTMPose / rtmlib，ONNX 推論）與姿態序列的力學特徵工程。
- 單一 sport-conditioned 時序模型：共用骨幹 + 運動項目條件 + 共用事件輸出頭 + 遮罩。
- 順序約束解碼：保證輸出事件符合宣告的時序。
- 資料集轉接層：GolfDB（真人標註）、Penn Action（弱標註）。
- 訓練、評估（PCE）、單支影片推論的 CLI。
- 事件註冊表：以宣告式資料定義每個運動的事件集合、順序與弱標註規則。

### Out of Scope

- 運動項目自動辨識、多人追蹤、球體/球具偵測。
- 3D 姿態、多機位、相機標定。
- 即時串流推論。
- 網頁前端。

## Requirements and Constraints

- Runtime：Python 3.12，conda 環境 `kinetic-chain`。
- 硬體：NVIDIA RTX 3070 8GB。模型必須能在此顯存內訓練，且姿態抽取需可用 GPU。
- 姿態抽取不自行訓練，使用 RTMPose 既有權重（與 `movement-coach` 相同的 rtmlib 路線）。
- 核心層為純 Python 套件，可直接 `import kinetic_chain` 使用，不依賴任何服務。
- 資料集不納入版本控制。輸入影片可能含可識別個人，不得提交。
- 弱標註（由運動學訊號程式化推導的事件）必須在資料結構、文件與評估結果中與真人標註
  明確區分，不得混報為同一件事。

## Success Criteria

| # | 標準 | 結果 |
|---|---|---|
| S1 | 同一套流程可訓練出多個運動各自的模型 | **達成**：6 個運動走同一份程式與指令 |
| S2 | 高爾夫 PCE 與 SwingNet 基準（71.5% 無增強 / 76.1% 有增強）可比較 | **達成**：四折平均 78.7% |
| S3 | 新增運動項目只需修改事件註冊表與新增資料轉接，不動模型與訓練程式 | **部分達成**（見下） |
| S4 | 跨運動聯合訓練不劣於單運動訓練 | **未達成**：劣 1.6 個百分點 → 單運動訓練為預設 |
| S5 | 輸出事件順序恆符合宣告時序 | **達成**：1854 段驗證片段，違反數 0 |
| S6 | 由別的運動預訓練再微調，優於從頭訓練 | **未達成**：各資料量下差異皆在雜訊內 |

數字與實驗設計見 `docs/architecture.md` 的 Verification and Experiments。

S2 的比較有前提：相同的是資料集、四折切分協定與 PCE 定義；不同的是輸入模態（本專案吃
2D 姿態，SwingNet 吃 RGB）與模型架構。SwingNet 的數字引自論文與作者 repo，未在本機重跑。
屬於參考基準，不是嚴格對照。

S3 只算部分達成：六個運動的註冊確實只動了 `events.py` 與 `datasets/`，但過程中必須修掉
`SportSpec.layout` 這個設計錯誤（關鍵點布局屬於資料來源而非運動項目——同一個運動可以
同時來自 Penn Action 與 GolfDB，布局不同）。抽象本身有缺陷時，S3 不會自動成立。

S4 未達成的原因已定位：主要不是跨運動共用本身（那只佔 0.6 個百分點），而是 Penn Action
高爾夫的弱標註與 GolfDB 的真人標註灌進同一個事件槽，但兩者的事件定義不一致（佔 1.0 個
百分點）。既然單運動訓練本來就比較好，且那正是使用者要的用法，此路線不再追。

S6 也未達成：以五個運動預訓練再微調高爾夫，在 25/50/100/200/400/1042 段六個資料量下
與從頭訓練的差距全部在標準差以內。合理的解釋是模型吃的已經是**手工設計的、與運動無關的
力學特徵**，骨幹本來就沒剩多少「通用動作表徵」可學；能學的只有「哪個訊號對應哪個事件」，
而那是每個運動各自的知識。實務結論：**新運動就直接標資料訓練，不必先預訓練。**

## Open Questions

- **共用事件槽的前提是事件定義一致，目前沒有機制表達這件事。** `SportSpec` 只宣告事件
  id，無法宣告「這個來源的這個事件與另一個來源的定義不相容」。可能的做法：依
  `label_source` 給不同的損失權重，或在定義衝突時讓同一事件分裂成不同的槽。這是 S4
  未達成的直接原因。
- **`address` 與 `finish` 的 PCE 只有 0.40 左右**，是整體分數的瓶頸；其餘六個事件平均
  0.91。這兩個事件缺乏明確的力學界線（球員可以靜止數十影格），把它們當成單一影格來預測
  可能就是錯的問法——也許該改成預測一個區間。SwingNet 有同樣的困難，說明這不是本方法
  特有的問題。
- 弱標註的品質仍未經人工抽檢。且弱標註的近端到遠端順序是**建構進去**的（在加速階段內
  搜尋峰值），因此不能拿這批標註來檢驗近端到遠端假說。
- 2D 影像下骨盆與軀幹的旋轉角速度只能由關鍵點連線的方向角推得，鏡頭非正對時失真程度
  未量化。這已經是實務上的痛點：弱標註規則必須由遠端往近端求解，正是因為髖線與肩線的
  方向角在側面視角不可靠。
- 事件容忍度（PCE 的 ±n frames）目前沿用 GolfDB 的定義以維持可比性，但該定義綁在
  「準備到擊球」這個區間上，對沒有明確擊球點的運動是否合適，未檢驗。
- 尚未在 GolfDB／Penn Action 以外的真實影片上測試。
- 跨運動微調在本設定下沒有效益（S6）。尚未檢驗的替代做法：把姿態序列直接餵給模型
  （不做手工特徵），讓骨幹自己學表徵——那種設定下預訓練可能才有意義。這會是另一個
  設計方向，不是本版的小修。
